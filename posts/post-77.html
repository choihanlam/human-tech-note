정상적인 API 요청은 왜 보안 위협이 되는가

AI 에이전트 시대, WAF·IPS 이후의 접근통제와 행위 기반 보안

2026년 11월 6일약 5분#77

공격은 반드시 비정상적인 요청으로 시작할까?

공격자가 정상 사용자와 동일한 방식으로 서비스를 이용한다면, 기존 보안 솔루션은 무엇을 기준으로 공격을 구분할 수 있을까? 방화벽·IPS·WAF는 중요한 방어선이지만 모든 공격이 명확한 악성 문자열을 포함하지는 않는다. 유효한 세션에서 정상 API를 호출하더라도 객체별 권한 검증이 부족하면 다른 사람의 정보에 접근할 수 있다.

WAF를 통과했다는 것은 안전하다는 의미일까?

구매내역 조회 API를 생각해 보자. 로그인 여부만 확인하고 요청한 구매내역의 소유권을 검증하지 않으면 BOLA(Broken Object Level Authorization) 위험이 발생한다. 인증은 요청자가 누구인지, 인가는 그 요청자가 해당 데이터에 접근해도 되는지 확인한다. WAF가 애플리케이션의 모든 업무 권한을 대신 판단할 수는 없다. 서버 측 객체 단위 인가 검증이 필요하다.

AI 에이전트는 무엇을 바꾸는가?

브라우저 자동화와 API 분석은 AI 이전에도 존재했다. AI 에이전트는 화면, 요청 구조, 사용자 동작을 해석하고 반복적인 분석을 자동화할 수 있다. 정상적인 보안점검에도 활용되지만 악용될 가능성도 있다. 그러나 AI가 생성한 요청이 탐지 불가능한 것은 아니다. 요청 빈도, 접근 대상, 세션 변화, 비정상적인 업무 흐름은 여전히 탐지 근거다.

단일 로그가 아니라 세션의 흐름을 보아야 한다

정상 로그인 → 개인정보 조회 API 호출 → 여러 객체에 대한 연속 접근 → 평소와 다른 조회 범위 → 일부 권한 검증 실패라는 가상 시나리오를 보자. WAF, API Gateway, 애플리케이션 인증·인가, DB 접근 로그를 사용자·세션·시간·객체 기준으로 연계하면 개별 요청에서는 보이지 않던 이상행위를 조사할 수 있다. 다만 대량 조회가 언제나 공격은 아니다. 관리자 업무나 배치 처리도 고려해야 한다.

WAF 요청 로그 → API 호출 로그 → 인증·인가 결과 → DB 접근 로그 → 세션 단위 상관분석

기술통제에서 개발·운영 거버넌스로

먼저 중요 API와 개인정보·결제·계정변경·다운로드 기능을 식별하고 권한 모델을 정의해야 한다. 개발·배포 단계에서는 서버 측 인가 검증을 테스트하고, 운영 단계에서는 요청과 데이터 접근 로그를 연결해야 한다. 탐지 후 판단과 조치의 책임도 명확해야 한다. 서비스 기획, 개발, 인프라, 보안 조직이 API의 업무적 의미와 통제 기준을 함께 관리해야 하는 이유다.

보안투자의 방향도 달라져야 한다

이미 WAF와 IPS를 운영한다면 솔루션 추가 이전에 기존 통제의 사각지대를 확인할 필요가 있다. API 자산 목록이 불완전하거나 인가 검증이 누락되고 로그 연계가 어렵다면 장비를 추가해도 근본적인 위험이 남는다. 중요 API 식별률, 인가 검증 테스트 범위, 이상행위 조사 소요시간, 개선조치 완료율 등 검증 가능한 운영 지표를 투자 우선순위와 연결할 수 있다.

마치며

방화벽과 WAF는 여전히 중요한 보안 통제다. 그러나 네트워크 요청이 허용되었다는 사실이 업무상 정당성까지 보장하지는 않는다. 보안의 질문은 ‘공격처럼 보이는 요청인가?’에서 ‘허용된 사용자에게 정당한 행위인가?’까지 확장되어야 한다.

참고한 연구와 자료

  1. OWASP · API1:2023 Broken Object Level Authorization
  2. OWASP · API6:2023 Unrestricted Access to Sensitive Business Flows

본문의 API 조회 사례는 설명을 위한 가상 시나리오이며 특정 기업의 실제 침해사고를 의미하지 않습니다.
