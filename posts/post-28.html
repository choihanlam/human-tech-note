기술부채는 왜 보안부채가 되는가

Legacy Architecture·예외·수작업·낮은 가시성이 시간이 지나며 Security Risk와 변경비용으로 전환되는 과정

2026년 11월 4일 약 14분#28 / 75
이 글의 구조
1. 1. SEI가 말하는 Technical Debt의 핵심은 ‘미래 변경비용’이다2. 2. 보안부채는 ‘통제를 못 했다’보다 ‘통제를 적용하기 점점 어려워지는 상태’다3. 3. 예외는 부채의 ‘이자’처럼 작동한다4. 4. Debt를 ‘보안예산’과 ‘Modernization 예산’으로 나누면 우선순위가 왜곡될 수 있다5. 5. 부채를 줄이는 가장 현실적인 방법은 ‘다음 변경에서 더 나쁜 부채를 만들지 않는 것’이다

기술부채는 흔히 ‘빠르게 개발한 대가로 나중에 갚아야 할 유지보수 비용’으로 설명된다. 실제 조직에서는 오래된 Framework, 수동배포, 공유계정, 예외 Firewall Rule, EOL 장비처럼 다양한 형태로 쌓인다.

흥미로운 점은 이 부채가 개발생산성 문제로만 남지 않는다는 것이다. 오래된 인증방식 때문에 MFA를 붙일 수 없고, 수동배포 때문에 보안설정이 서버마다 다르고, 예외가 많아져 실제 공격면을 알기 어려워지면 기술부채는 보안부채로 전환된다.

그래서 Modernization과 Security Investment를 따로 보는 대신 기술부채가 어떤 경로로 Security Risk를 키우는지 살펴볼 필요가 있다.

이 글의 중심 질문
기술부채가 Security Debt로 전환되는 경로를 가시화하고, 이를 Architecture·보안·투자 포트폴리오의 공통언어로 사용할 수 있는가?

1. SEI가 말하는 Technical Debt의 핵심은 ‘미래 변경비용’이다

CMU Software Engineering Institute는 Technical Debt를 단기 편익을 위해 장기적인 수정·유지·진화 비용을 높이는 Trade-off로 설명한다. 부채 자체가 항상 나쁜 것은 아니다. 의도적으로 선택하고 갚을 계획이 있다면 전략적 선택이 될 수 있다.

문제는 부채가 어디에 있는지 모르거나 상환계획 없이 계속 누적될 때다. 이때 새로운 요구사항 하나를 반영하기 위해 더 많은 예외와 우회가 필요해진다.

보안에서도 동일하다. 새로운 MFA, 암호표준, Logging 요구를 적용할 때 Legacy 때문에 별도 예외를 만들게 되면 Security Change Cost가 계속 올라간다.

2. 보안부채는 ‘통제를 못 했다’보다 ‘통제를 적용하기 점점 어려워지는 상태’다

오래된 Application이 Modern Authentication을 지원하지 않으면 별도 VPN이나 공유계정을 유지해야 할 수 있다. EOL OS가 새 EDR Agent를 지원하지 않으면 Network Isolation과 수동점검을 추가한다.

각 보완통제는 단기적으로 Risk를 줄이지만 Architecture 복잡성을 높인다. 새로운 통제를 도입할 때 다시 이 예외들을 고려해야 한다.

따라서 Security Debt를 단순 취약점 개수보다 ‘새로운 보안기준을 적용하는 데 드는 추가비용’으로 정의해볼 수 있다.

3. 예외는 부채의 ‘이자’처럼 작동한다

Legacy를 유지하기 위해 만든 예외 ACL, 별도 Monitoring, Manual Review는 매월 운영비용을 발생시킨다. 시스템이 오래될수록 이 주변 통제가 더 늘어난다.

이 비용은 예산서에서 ‘Legacy 이자’로 보이지 않는다. 여러 팀의 작은 수작업과 장애위험으로 분산되기 때문이다.

Technical Debt Register에 운영시간·예외개수·Incident 영향·신규통제 적용난이도를 함께 기록하면 보이지 않던 이자를 드러낼 수 있다.

Operational Interest

반복 수작업·점검시간

02

Security Interest

추가 보완통제·예외관리

03

배포·패치·마이그레이션 위험

04

Opportunity Cost

신규기술·자동화 도입이 늦어지는 비용

4. Debt를 ‘보안예산’과 ‘Modernization 예산’으로 나누면 우선순위가 왜곡될 수 있다

보안팀은 위험을 줄이고 싶고 IT는 노후시스템을 교체하고 싶다. 동일한 Legacy 문제를 서로 다른 예산언어로 설명하면 투자안이 분리된다.

예를 들어 EOL 서버 교체는 인프라 Modernization이면서 Patch Risk 감소, EDR Coverage 향상, 운영자동화 기반 구축이라는 보안효과도 가진다.

Portfolio 평가에서 Risk Reduction과 Delivery Efficiency, Future Readiness를 함께 넣으면 한 프로젝트의 다중효과를 설명할 수 있다.

5. 부채를 줄이는 가장 현실적인 방법은 ‘다음 변경에서 더 나쁜 부채를 만들지 않는 것’이다

모든 Legacy를 한 번에 교체하는 것은 현실적이지 않다. 따라서 신규프로젝트에 Secure Default, Standard Identity, Logging, IaC, API를 적용해 새로운 부채의 생성을 줄이는 것이 중요하다.

기존 Debt는 Register로 관리하고 시스템 변경·계약갱신·EOL 시점에 상환기회를 연결할 수 있다.

이렇게 하면 Technical Debt Management가 별도 정비프로젝트가 아니라 Portfolio와 Architecture Review의 반복적인 기준이 된다.

RESEARCHER'S NOTE

IT 인프라 개선과 보안운영을 모두 경험하면서, 많은 보안예외가 보안팀이 만든 것이 아니라 과거 Architecture의 제약에서 시작된다는 점을 자주 봤다. 그래서 보안문제를 솔루션 추가만으로 해결하려 하면 예외가 더 복잡해질 수 있다.

기술부채를 경영언어로 바꾸는 작업은 단순히 오래된 시스템을 비판하는 것이 아니라 ‘지금 갚지 않으면 앞으로 어떤 선택을 잃게 되는가’를 설명하는 데 있다고 본다.

기술부채와 보안취약점 사이의 상관이 모든 시스템에서 동일하게 나타나는 것은 아니다. Debt Register가 또 다른 문서작업으로 끝나지 않으려면 실제 Incident·Change·운영시간 데이터와 연결되어야 한다.
