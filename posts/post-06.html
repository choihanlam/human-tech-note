AI 에이전트에게 권한을 어디까지 줄 것인가

Identity, Delegation, Approval 그리고 Accountability — Agentic AI 시대의 접근통제를 기업 거버넌스 관점에서 다시 보기

2026년 11월 4일 약 10분 최한람
Research Note
이 글은 2026년 NIST의 AI Agent Standards Initiative와 NCCoE의 Software and AI Agent Identity and Authorization 자료, OAuth 2.0 Token Exchange, Zero Trust와 Continuous Access Evaluation 개념을 바탕으로 기업 환경의 Agent 권한통제를 재구성한 글입니다. Agent Identity 관련 표준은 현재도 빠르게 발전하고 있으므로, 아래의 통제모델은 특정 제품의 구현방법보다 의사결정 원칙에 초점을 둡니다.

생성형 AI가 문서를 요약하거나 답변을 만들어주는 단계에서는 사용자가 결과를 확인한 뒤 직접 행동할 수 있었다. Agentic AI는 이 경계를 바꾼다. 에이전트가 이메일을 보내고, 캘린더를 수정하고, 코드를 배포하고, 보안 이벤트를 분석해 실제 조치까지 수행하기 시작하면 질문의 중심은 모델의 정확도에서 행동할 권한을 누구에게, 어떤 조건으로 위임할 것인가로 이동한다.

NIST는 2026년 AI Agent Standards Initiative를 시작하면서 AI 에이전트가 사용자를 대신해 외부 시스템과 내부 데이터에 접근하는 환경에서 보안성과 상호운용성을 주요 과제로 제시했다. 같은 해 NCCoE는 Agent Identity와 Authorization을 별도 프로젝트 주제로 다루기 시작했고, 600건이 넘는 의견을 수렴한 뒤 위임과 책임추적을 핵심 쟁점으로 정리했다.

RESEARCH QUESTION
AI Agent가 사용자를 대신해 Tool·API·Data에 접근하고 실제 변경을 수행할 때, 조직은 “누가 누구에게 어떤 권한을 왜, 언제까지 위임했는가”를 어떻게 통제하고 증명할 것인가?

1. Agent Identity는 하나의 계정으로 설명하기 어렵다

기존 IAM에서는 사람의 계정과 서비스 계정을 구분하고 각각 Role이나 Permission을 부여하는 방식이 일반적이었다. Agentic AI에서는 여기에 위임된 권한과 실행 맥락이 추가된다. 같은 에이전트라도 어떤 사용자를 대신하는지, 어떤 업무를 수행하는지, 어떤 Tool과 Data에 접근하는지에 따라 허용 범위가 달라질 수 있기 때문이다.

01 · PRINCIPAL
Human / Organization
업무를 요청하고 최종 책임을 갖는 사람 또는 조직
02 · WORKLOAD
Agent Identity
실제로 실행되는 에이전트·서비스·런타임의 식별자
03 · AUTHORITY
Delegated Authority
누구를 대신해 어느 범위까지 행동할 수 있는지 나타내는 권한
04 · CONTEXT
Task Context
목적·대상·시간·데이터 민감도·위험수준 등 실행 조건

NIST NCCoE가 2026년 제시한 질문도 이 구조와 맞닿아 있다. 에이전트의 식별정보를 어떻게 정의할지, 에이전트의 Identity를 특정 런타임이나 조직 경계에 묶을지, 사람의 Identity와 Agent Identity를 어떻게 연결해 Human-in-the-loop 승인을 지원할지 등이 주요 검토대상이다.

KEY POINT
“이 에이전트가 누구인가”와 “이 에이전트가 지금 무엇을 할 수 있는가”를 분리해 관리한다.

Identity는 실행 주체를 식별하고, Authorization은 특정 자원·행동·맥락에 대한 허용범위를 결정한다. Agentic AI에서는 두 정보를 연결하되 동일한 개념으로 취급하지 않는 것이 중요하다.

2. 인증에 성공했다고 행동할 권한이 생기는 것은 아니다

에이전트가 인증서를 제시하거나 OAuth Client로 인증에 성공하면 시스템은 해당 실행주체를 식별할 수 있다. 그러나 인증 결과만으로 메일 발송, 파일 삭제, 운영 배포, 계정 잠금 같은 행동까지 허용하면 권한의 범위가 지나치게 넓어진다.

예를 들어 개발 지원 에이전트가 Repository를 읽을 수 있는 권한과 Production 배포를 실행할 수 있는 권한은 별개의 판단이어야 한다. 보안운영 에이전트 역시 SIEM 이벤트 조회와 EDR 단말 격리 사이에는 다른 승인기준이 필요하다. 읽기·추천·변경·파괴적 조치가 하나의 Role 안에 섞이면 Agent의 편의성은 높아지지만 통제가능성은 급격히 낮아진다.

행동 수준예시권장 통제

3. 핵심은 ‘권한 복제’보다 ‘위임’을 설계하는 데 있다

Agent가 사용자를 대신해 행동하는 가장 단순한 방법은 사용자의 기존 Credential이나 넓은 Access Token을 그대로 사용하는 것이다. 하지만 이 방식에서는 사용자의 전체 권한과 Agent가 특정 업무에 필요한 권한 사이의 경계가 흐려진다.

OAuth 2.0 Token Exchange(RFC 8693)는 subject와 actor를 구분해 위임관계를 표현할 수 있는 기반을 제공한다. 사용자 또는 원래 권한주체를 subject로, 실제 행동하는 시스템을 actor로 기록하고, 필요한 대상(resource/audience)과 범위(scope)에 맞는 새로운 Token을 발급하는 방식이다. JWT의 act claim은 현재 Actor와 위임체인을 표현할 수 있다.

DESIGN PRINCIPLE
Agent에게 “사용자의 권한”을 주기보다 “이번 업무에 필요한 권한”을 발급한다.

대상 시스템, 허용 Action, 데이터 범위, 사용 목적과 유효시간을 좁게 정의하면 Agent의 자율성과 최소권한을 함께 관리할 수 있다. 장기 Credential보다 짧은 수명의 위임 Credential을 우선하는 이유도 여기에 있다.

4. Human-in-the-loop는 모든 행동을 사람이 승인하는 구조가 아니다

Agent의 모든 Tool 호출을 사람이 확인한다면 통제는 쉬워 보이지만 자동화의 가치가 크게 줄어든다. 반대로 한 번 승인한 뒤 모든 후속행동을 자동으로 허용하면 Agent가 경로를 바꾸거나 새로운 Tool을 선택했을 때 처음의 의도와 실제 실행 사이에 간극이 생길 수 있다.

따라서 Human-in-the-loop는 위험수준에 따라 승인경계를 설계하는 문제로 보는 편이 적절하다. 낮은 위험의 조회는 정책으로 자동 승인하고, 외부 전송·운영 변경·권한상승처럼 영향이 큰 행동에서만 사람이 개입하는 방식이다.

LOW RISK
Policy-based Auto Approval
정해진 Data와 Tool 안에서의 조회·분석. 허용범위와 TTL을 사전에 제한하고 자동 수행한다.
MEDIUM RISK
Conditional Approval
대상·시간·업무상태·사용자 Context가 정책조건을 충족할 때 수행한다.
HIGH RISK
Step-up Human Approval
외부 발송, 운영 변경, 사용자 차단처럼 영향이 큰 행동은 실행 직전 승인을 받는다.
PRIVILEGED
Dual Control / JIT
권한상승·Credential·대량삭제 등은 이중통제와 Just-in-Time 권한, 사후검토를 결합한다.

5. 권한은 한 번 평가하고 끝나는 값이 아니다

Agentic Workflow는 실행 도중 새로운 데이터를 읽고, 다른 Tool을 선택하고, 다른 Agent에게 작업을 넘길 수 있다. 시작 시점에는 허용된 업무라도 중간 Context가 바뀌면 동일한 권한판정이 계속 유효하다고 보기 어렵다.

NIST SP 800-207의 Zero Trust는 접근을 고정된 신뢰가 아니라 지속적으로 평가되는 정책결정으로 본다. OpenID의 Continuous Access Evaluation Profile(CAEP)도 사용자·디바이스·세션·애플리케이션 상태 변화에 따라 접근을 축소하거나 재평가할 수 있는 이벤트 기반 구조를 제시한다.

CONTINUOUS AUTHORIZATION
“시작할 때 허용되었는가?”에서 “지금도 이 행동이 허용되는가?”로 질문을 바꾼다.

Tool 변경, 대상 자원 변경, 데이터 민감도 상승, 비정상 행동, 사용자 상태변경, 세션 위험도 상승 같은 이벤트를 정책결정에 반영하면 Agent의 실행경로가 바뀌어도 권한을 다시 평가할 수 있다.

기업 환경에서는 모든 Tool 호출마다 복잡한 정책엔진을 두는 방식보다, 보안경계와 고위험 Action을 중심으로 재평가 지점을 설계하는 것이 현실적이다. 예를 들어 읽기에서 쓰기로 전환되는 순간, 내부 데이터가 외부 API로 이동하는 순간, 다른 Agent에게 권한을 다시 위임하는 순간을 Policy Enforcement Point로 볼 수 있다.

6. 로그에는 ‘무엇을 했는가’와 함께 ‘왜 할 수 있었는가’가 남아야 한다

기존 감사로그는 누가 언제 어떤 API를 호출했는지 기록하는 데 집중해왔다. Agentic AI에서는 여기에 요청의 의도와 위임근거, 정책판정, 승인상태까지 연결해야 책임성을 설명할 수 있다.

NIST가 2026년 수렴한 이해관계자 의견에서도 단순 Action Log를 넘어 어떤 요청이 평가되었는지, 어떤 Identity와 Delegation이 관련되었는지, 어떤 Policy Decision과 Human Approval이 있었는지를 함께 남겨야 한다는 요구가 반복적으로 나타났다.

Authority Evidence누가 업무를 요청했고 어떤 Agent에게 어떤 Scope를 위임했는가
Decision Evidence어떤 Policy와 Context를 기준으로 허용·거부·승인이 결정되었는가
Execution Evidence어떤 Tool·Data·API에 어떤 Action을 수행했고 결과는 무엇이었는가

Intent / Purpose어떤 업무 목적과 사용자 요청을 근거로 행동했는가?

7. 기업이 가져갈 수 있는 Agent 접근통제 원칙

Agentic AI의 IAM을 새로운 제품군으로만 접근하면 기존의 계정관리·접근통제·Zero Trust와 단절될 수 있다. 오히려 기존 통제원칙을 Agent의 특성에 맞게 확장하는 편이 구조적으로 안정적이다.

01 · IDENTITY
Agent를 별도 실행주체로 식별한다
공용 계정이나 사용자의 Credential을 공유하지 않고 Agent·Workload별 Identity와 Lifecycle을 관리한다.
02 · DELEGATION
권한은 복제보다 위임으로 전달한다
Scope·Audience·TTL·Purpose를 제한한 Delegated Credential을 사용하고 위임체인을 추적한다.
03 · APPROVAL
위험기반 승인경계를 둔다
조회·추천·변경·특권행동을 구분하고 영향이 큰 Action에 Step-up Approval을 적용한다.
04 · CONTEXT
실행 중에도 권한을 재평가한다
Tool·Data·대상·위험도가 바뀌면 정책을 다시 평가하고 필요 시 Scope를 축소하거나 세션을 중단한다.
05 · ACCOUNTABILITY
행동과 권한근거를 하나의 증적체인으로 남긴다
요청자·Agent·위임·정책판정·승인·Action·결과를 연결해 사후 설명가능성을 확보한다.
06 · REVOCATION
권한회수도 설계의 일부로 본다
사용자 상태변경, 위험 이벤트, 업무 종료 시 Token·Session·Agent Entitlement를 즉시 회수할 수 있어야 한다.
DECISION FRAME
Agent 접근통제의 단위는 ‘계정’이 아니라 ‘주체 × 행동 × 목적 × 맥락 × 시간’이다.

기업이 Agent에게 권한을 줄 때는 “이 Agent를 신뢰할 수 있는가”만 확인하기보다, 특정 Principal을 대신해 특정 목적의 특정 Action을 어느 자원에 언제까지 수행하도록 허용할 것인지 구조화하는 편이 적절하다.

마치며: 자율성을 키울수록 권한의 경계는 더 구체적이어야 한다

Agentic AI의 가치는 사람이 하던 여러 단계를 연결하고 실제 행동까지 수행하는 데 있다. 자율성이 높아질수록 조직은 더 많은 작업을 자동화할 수 있지만, 동시에 한 번의 잘못된 권한판정이 여러 시스템과 데이터로 연쇄될 가능성도 커진다.

따라서 Agent 보안의 핵심은 모든 행동을 막거나 모든 판단을 사람에게 되돌리는 데 있지 않다. 자율적으로 수행해도 되는 영역을 명확히 정의하고, 그 경계를 넘는 순간 다시 권한과 책임을 확인하는 구조를 만드는 데 있다.

AI Agent에게 줄 수 있는 가장 좋은 권한은 ‘많은 권한’도 ‘적은 권한’도 아니다.
누구를 대신해, 어떤 목적과 조건으로, 어디까지 행동할 수 있는지가 설명되는 권한이다.

이 관점에서 Agent Identity는 IAM의 새로운 객체이고, Delegation은 권한 전달의 핵심 메커니즘이며, Approval은 위험기반 의사결정 지점이고, Accountability는 전체 실행을 조직의 책임체계와 연결하는 마지막 고리다. 결국 Agentic AI의 접근통제는 보안설정의 문제가 아니라 조직이 자동화된 의사결정권을 어떻게 배분할 것인가라는 IT Governance의 문제로 이어진다.
