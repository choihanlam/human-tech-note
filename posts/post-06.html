AI 에이전트에게 권한을 어디까지 줄 것인가

Identity, Delegation, Approval, Accountability — ‘잘 대답하는 AI’에서 ‘행동하는 AI’로 넘어갈 때 접근통제는 어떻게 바뀌어야 하는가

생성형 AI가 문서를 요약하고 답변을 만들어주는 단계에서는 오류가 발생해도 사람이 마지막에 멈출 수 있었다. 그러나 에이전트가 이메일을 보내고, 캘린더를 수정하고, 코드를 배포하고, 티켓을 닫고, 보안 이벤트에 대응하기 시작하면 문제가 달라진다. 이제 AI는 정보를 생성하는 도구가 아니라 조직의 권한을 사용해 상태를 바꾸는 실행 주체가 된다.

정보보호 실무에서 접근통제를 다뤄보면 권한은 계정에 붙어 있는 정적인 속성이 아니라는 점을 자주 확인하게 된다. 누가, 어떤 목적으로, 어느 시스템에, 얼마 동안 접근하는지에 따라 같은 계정도 위험도가 달라진다. Agentic AI는 이 문제를 더 복잡하게 만든다. 사람의 의도를 받아 스스로 Tool을 선택하고, 다른 Agent나 API에 작업을 넘기며, 중간 결과에 따라 다음 행동을 바꿀 수 있기 때문이다.

그래서 이 글에서는 ‘AI Agent에게 최소권한을 주자’는 원칙만 반복하지 않는다. 실제 기업에서 최소권한을 구현하려면 무엇을 식별해야 하고, 권한을 어떻게 위임해야 하며, 어느 순간 사람의 승인을 요구하고, 나중에 책임을 어떻게 재구성할 수 있어야 하는지를 하나의 흐름으로 보려 한다.

이 글의 중심 질문
AI Agent가 사용자를 대신해 Tool·API·Data에 접근하고 실제 변경까지 수행할 때, 조직은 ‘누가 누구에게 어떤 권한을 왜, 언제까지 위임했는가’를 어떻게 통제하고 나중에 증명할 것인가?

1. NIST가 2026년에 ‘Agent Identity’를 별도 주제로 꺼낸 이유

2026년 2월 NIST는 AI Agent Standards Initiative를 발표하면서 Agent가 외부 시스템과 내부 데이터에 안전하게 접근하고 상호운용되는 문제를 핵심 과제로 제시했다. 이어 NCCoE는 Software and AI Agent Identity and Authorization concept paper를 통해 identification, authentication, authorization, auditing, non-repudiation을 별도의 연구·구현 영역으로 다루기 시작했다.

이 움직임이 흥미로운 이유는 Agent 보안을 Prompt Injection이나 모델 안전성만의 문제로 다루지 않는다는 데 있다. NIST가 바라보는 Agent는 모델이 아니라 도구·데이터·권한을 이용해 실제 환경을 바꾸는 소프트웨어 주체다. 따라서 Agent Security는 기존 IAM·Zero Trust·Audit 체계와 연결되어야 한다.

2026년 10월 NIST가 공개한 Agent Identity Management 설계 원칙에서도 Distinct Agent Identification, Human-in-the-Loop Trigger, Mandates and Constraints, Policy와 Reasoning의 구조적 분리가 강조된다. ‘LLM이 무엇을 하려는가’와 ‘시스템이 무엇을 허용하는가’를 분리해야 한다는 점은 기존 접근통제의 오래된 원칙을 Agent 환경에 다시 적용한 것으로 볼 수 있다.

2. 사람의 계정을 Agent가 그대로 쓰면 무엇이 사라지는가

가장 쉬운 구현은 사용자의 기존 Credential이나 광범위한 Access Token을 Agent에게 넘기는 방식이다. 기능은 빠르게 붙는다. 그러나 이 순간부터 ‘사용자가 직접 한 행동’과 ‘Agent가 사용자를 대신해 한 행동’이 로그에서 구분되지 않을 수 있다. 권한의 주체와 실행의 주체가 섞이는 것이다.

실무에서 중요한 것은 Agent가 사람과 같은 권한을 갖는지가 아니라 이번 업무에 필요한 권한만 별도로 발급받는가다. OAuth 2.0 Token Exchange(RFC 8693)의 subject–actor 구조는 이 문제를 설명하기 좋은 모델이다. 원래 권한주체(subject)와 실제 행동주체(actor)를 구분하고, resource·audience·scope가 제한된 토큰을 다시 발급할 수 있다.

이렇게 보면 Agent Identity는 Service Account의 다른 이름이 아니다. 누가 업무를 시켰고, 어떤 목적이었고, 어느 Tool에 어떤 Scope로 접근했는지까지 연결되는 ‘위임된 행위자’라는 성격이 더 강하다.

구분기존 자동화Agentic AI에서 추가로 필요한 질문
실행주체Service Account / BatchAgent 자체의 고유 식별자가 있는가?
권한Role 또는 API Key요청자의 의도와 Scope가 위임에 반영되는가?
행동사전 정의된 ScriptAgent가 Tool·순서를 동적으로 바꿀 수 있는가?
감사누가 API를 호출했는가누가 요청했고, Agent는 무엇을 판단했으며, 어떤 승인으로 행동했는가?

3. ‘Human-in-the-loop’는 모든 클릭을 사람이 승인한다는 뜻이 아니다

Agent의 모든 Tool 호출을 사람이 승인하면 통제는 강해 보이지만 자동화 가치는 거의 사라진다. 반대로 첫 요청 한 번만 승인하고 이후 행동을 모두 허용하면 Agent가 업무범위를 넓히거나 새로운 Tool을 선택할 때 원래 의도와 실제 실행 사이에 간극이 생길 수 있다.

따라서 Human-in-the-loop는 승인 횟수의 문제가 아니라 위험 임계값을 어디에 둘 것인가의 문제다. 조회·분석은 자동화하고, 외부 전송·운영 변경·권한상승·대량 삭제처럼 영향이 큰 행동에서만 Step-up Approval을 요구하는 식이다.

NIST가 최근 강조하는 것도 같은 방향이다. 승인 요청이 너무 자주 발생하면 사용자는 습관적으로 승인하게 되고, 결국 통제는 형식화된다. 보안통제는 ‘승인 화면을 하나 더 띄우는 것’이 아니라 사람이 개입해야 할 지점을 위험기반으로 정하는 일이어야 한다.

4. 정책은 LLM의 Reasoning 바깥에 있어야 한다

Agent가 Prompt Injection을 받았을 때 가장 위험한 구조는 모델이 ‘무엇을 할지’뿐 아니라 ‘무엇을 할 수 있는지’까지 스스로 결정하는 경우다. 모델의 출력이 Credential 선택이나 권한확장으로 바로 연결되면 악성 입력이 통제평면까지 영향을 줄 수 있다.

그래서 Authorization Policy와 Credential은 Reasoning Model 바깥에 두어야 한다. Agent가 어떤 Tool을 호출하려 해도 별도의 Policy Enforcement Point가 Principal, Agent, Resource, Action, Purpose, Session Risk를 평가해 허용여부를 결정하는 구조가 필요하다.

이 원리는 Zero Trust와도 연결된다. 신뢰는 ‘이 Agent가 우리 조직에서 만든 Agent이기 때문’에 주는 것이 아니라 매 행동마다 자원과 맥락에 맞게 판단한다. 특히 다른 Agent에게 작업을 위임하는 Multi-Agent 환경에서는 Delegation Chain이 길어질수록 이 분리가 중요해진다.

5. 로그에는 ‘무엇을 했는가’보다 ‘왜 할 수 있었는가’가 더 필요해진다

기존 API 로그는 Actor, Timestamp, Resource, Result 정도를 남기면 상당수 사건을 재구성할 수 있었다. Agent 환경에서는 같은 로그만으로는 부족하다. Agent가 어떤 사용자 요청을 근거로 행동했는지, 어떤 Mandate와 Scope가 있었는지, Policy Engine이 어떤 Context로 허용했는지, 사람의 승인이 있었다면 누가 승인했는지가 함께 필요하다.

이 정보가 있어야 사고 이후 책임을 단순히 ‘AI가 했다’로 끝내지 않고, 권한 설계와 승인 체계의 어느 지점에서 통제가 약했는지 찾을 수 있다. 결국 Accountability는 법무적인 사후 책임만을 의미하지 않는다. 시스템을 개선하기 위해 사건을 재현할 수 있는 기술적 증적체계를 의미한다.

개인적으로 Agent 보안에서 가장 중요한 자산은 Model 자체보다 Authority Graph라고 본다. 누가 누구에게 어떤 목적의 권한을 위임했고, 실제로 어느 자원에 어떤 행동이 발생했는지를 연결한 그래프가 있어야 Agent를 조직의 통제체계 안에 넣을 수 있다.

01

Authority Evidence

Principal, Agent ID, Mandate, Scope, TTL을 연결해 누가 어떤 권한을 만들었는지 남긴다.

02

Decision Evidence

Allow/Deny/Step-up을 결정한 Policy와 Context를 저장한다.

03

Execution Evidence

실제 Tool/API 호출, 대상 자원, 결과, Rollback 여부를 남긴다.

04

Learning Evidence

사고·오탐·예외 결과를 다음 Policy와 Risk Threshold 조정에 반영한다.

RESEARCHER'S NOTE

정보보호 실무에서는 ‘계정을 발급하고 권한을 검토한다’는 익숙한 통제가 실제 운영에서는 조직변경, 겸무, 외주, 예외승인 때문에 계속 흔들리는 것을 볼 수 있다. Agent는 이 오래된 IAM 문제를 더 빠르고 더 큰 규모로 재현할 가능성이 있다. 그래서 Agent Security를 완전히 새로운 분야로 보기보다, 기존 접근통제·최소권한·감사·변경관리의 원칙을 더 정교하게 적용하는 문제로 보는 편이 현실적이라고 생각한다.

다만 중요한 차이도 있다. 사람은 권한을 가진 뒤에도 업무 목적을 스스로 해석하지만, Agent는 Prompt·Context·Tool 결과에 따라 행동 경로를 빠르게 바꾼다. 따라서 Agent 시대의 IAM은 ‘계정에 Role을 붙이는 관리’에서 ‘의도와 맥락이 포함된 위임을 계속 검증하는 구조’로 발전해야 한다.

반론과 한계

LIMITATION

Agent Identity 표준과 프로토콜은 2026년 현재도 빠르게 형성되는 중이다. NIST의 Design Tenets 역시 구현표준이 완성됐다는 뜻이 아니라 안전한 IAM 구조를 위한 방향성을 제시하는 단계에 가깝다. 따라서 특정 Vendor의 Agent Platform 기능을 곧바로 업계 표준으로 해석하기보다, Identity·Delegation·Policy Separation·Audit라는 원칙이 실제 Architecture에서 어떻게 구현되는지를 지속적으로 확인할 필요가 있다.
