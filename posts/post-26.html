SASE·ZTNA는 VPN의 대체재인가

터널을 바꾸는 프로젝트가 아니라 Network-level Access를 Application·Identity 중심으로 재설계하는 과정

Research Archive · 2026년 10월 15일 약 12분#26 / 75
이 글의 구조
1. 1. VPN은 ‘연결’을 제공하고 ZTNA는 ‘접근결정’을 앞세운다2. 2. VPN 환경에서도 Zero Trust 원칙을 적용할 수 있다3. 3. SASE는 원격접속을 넘어 ‘정책 일관성’ 문제를 다룬다4. 4. Migration에서는 VPN과 ZTNA가 오랫동안 공존할 수 있다5. 5. 전환의 성공기준은 ‘VPN 제거율’보다 과도한 Trust 감소다

원격접속 보안을 개선할 때 VPN, ZTNA, SASE가 같은 제품군처럼 비교된다. ‘VPN을 없애고 ZTNA로 바꿀 것인가’라는 질문이 자연스럽게 나온다. 그러나 세 개념은 정확히 같은 범위를 다루지 않는다.

VPN은 네트워크 경로를 제공하고, ZTNA는 특정 Application 접근을 Identity와 Context 기반으로 통제하며, SASE는 ZTNA·SWG·CASB·FWaaS 같은 네트워크·보안기능을 Cloud-delivered 구조로 결합하는 더 넓은 운영모델이다.

그래서 전환의 핵심을 터널 기술로만 보면 실제 변화인 Access Scope와 Policy Decision의 이동을 놓치기 쉽다.

이 글의 중심 질문
VPN에서 ZTNA/SASE로의 전환을 제품교체가 아니라 ‘네트워크에 접속시키는 방식’에서 ‘필요한 Application만 조건부로 허용하는 방식’으로의 Architecture 변화로 볼 수 있는가?

1. VPN은 ‘연결’을 제공하고 ZTNA는 ‘접근결정’을 앞세운다

VPN은 사용자 단말과 내부 네트워크 사이에 암호화된 터널을 만든다. 이후 접근범위는 Firewall, Route, ACL, Application 인증으로 제어된다.

ZTNA는 접근 전에 Identity, Device State, Application을 확인하고 특정 Resource에 필요한 연결만 제공하는 것을 목표로 한다. 네트워크 전체를 보이게 하지 않고 Application-level Access로 Scope를 줄일 수 있다.

따라서 ZTNA의 가치가 ‘VPN보다 새로운 프로토콜’에 있는 것이 아니라 접근단위와 정책의 세밀함에 있다.

NIST SP 800-207

Zero Trust

Network Location의 암묵적 신뢰를 제거하고 Resource 중심 접근을 강조

CISA ZTMM 2.0

Maturity

Identity·Device·Network·Application·Data의 통합 성숙도 제시

SASE Architecture

Cloud-delivered Security

분산 사용자·SaaS·Branch·Cloud에 공통 정책 제공

2. VPN 환경에서도 Zero Trust 원칙을 적용할 수 있다

VPN을 사용한다고 반드시 Zero Trust와 반대되는 것은 아니다. VPN 접속 후에도 MFA, Device Compliance, 최소 Network Route, Application Authorization, Session Monitoring을 적용하면 신뢰범위를 줄일 수 있다.

반대로 ZTNA 제품을 도입했어도 모든 Application을 넓은 Policy로 허용하고 Device Context를 보지 않는다면 Zero Trust 수준이 낮을 수 있다.

따라서 Architecture 평가에서 제품명보다 실제 Access Path와 Policy를 봐야 한다.

질문전통 VPN 중심ZTNA 중심
접근 단위Network/SubnetApplication/Resource
신뢰 기준VPN 접속 + 계정Identity + Device + Context
노출 범위내부 Network Route 가능필요 Resource만 Broker
세션평가초기 인증 중심위험신호에 따른 재평가 가능

3. SASE는 원격접속을 넘어 ‘정책 일관성’ 문제를 다룬다

사용자는 본사·재택·모바일에서 SaaS와 Cloud, 내부 Application을 동시에 사용한다. 지점별 Appliance와 개별 VPN만으로는 정책이 분산되기 쉽다.

SASE는 Network와 Security Enforcement를 Cloud-delivered 구조로 통합해 사용자 위치와 관계없이 동일한 정책을 적용하려는 접근이다.

그러나 통합은 Vendor Lock-in, 장애영향, 데이터경로, 로그 통합과 같은 새로운 Architecture Risk도 만든다.

01

Policy Consistency

위치와 관계없이 동일한 Identity·Data Policy

02

Visibility

SaaS·Web·Private App 트래픽을 공통 Telemetry로 관찰

03

Operations

분산 Appliance 관리복잡성 감소 가능

04

Concentration Risk

단일 Provider 장애·정책오류의 Blast Radius 확대 가능

4. Migration에서는 VPN과 ZTNA가 오랫동안 공존할 수 있다

Legacy Protocol, 관리자 접속, 특정 Network Discovery가 필요한 시스템은 ZTNA로 즉시 전환하기 어렵다. 모든 Application을 한 번에 옮기려 하면 운영위험이 커진다.

외부 협력사, SaaS Admin, Web 기반 내부서비스처럼 Application 단위로 분리하기 쉬운 영역부터 ZTNA로 옮기고, Legacy는 VPN에 남기는 단계적 접근이 현실적이다.

이 과정에서 VPN 사용자·Route를 줄이는 것을 Migration KPI로 사용할 수 있다.

5. 전환의 성공기준은 ‘VPN 제거율’보다 과도한 Trust 감소다

VPN 사용자를 0명으로 만드는 것이 목적이 되면 Legacy 운영과 긴급관리 경로를 무리하게 제거할 수 있다. 더 중요한 지표는 User가 접근할 수 있는 Resource 범위가 얼마나 줄었는지, 미관리 Device가 차단되는지, Session Risk가 반영되는지다.

Access Graph를 전환 전후로 비교하면 사용자 한 명이 볼 수 있는 Network/Service 범위가 얼마나 축소됐는지 측정할 수 있다.

결국 Remote Access Modernization은 연결기술보다 Trust Surface를 줄이는 프로젝트다.

RESEARCHER'S NOTE

원격접속 취약점 이슈를 검토하고 ZTNA 계열 솔루션 PoC를 접하면서 느낀 점은 ‘VPN을 바꾸면 보안이 좋아진다’는 식으로 설명하기 어렵다는 것이었다. 실제 가치는 사용자와 Application 사이의 권한범위를 얼마나 세밀하게 줄이느냐에 있었다.

그래서 SASE/ZTNA를 네트워크 제품보다 Access Governance와 운영표준화의 관점으로 보는 편이 더 유용하다고 생각한다.

반론과 한계

LIMITATION

SASE와 ZTNA는 Vendor마다 기능범위와 용어가 다르며, 제품구조에 따라 Data Path와 성능·장애 특성이 크게 달라진다. 이 글은 특정 제품 비교가 아니라 Architecture 관점의 해석이다.
