클라우드 보안의 책임은 어디까지 공유되는가

Shared Responsibility 표 한 장으로는 부족하다 — Provider 경계와 내부 R&R·Decision Right·Evidence를 함께 보기

2026년 11월 4일 약 13분#24 / 75

클라우드의 Shared Responsibility Model은 단순해 보인다. Provider는 Cloud 자체의 보안을, 고객은 Cloud 안에서의 보안을 책임한다. 그런데 실제 운영에 들어가면 이 문장만으로 해결되지 않는 질문이 쏟아진다.

IAM 정책은 누가 설계하고 누가 정기검토해야 하는가? Network는 Platform팀이 관리하지만 Security Group 예외는 개발팀이 요청한다면 최종 Owner는 누구인가? SaaS의 Audit Log 설정은 IT가 할까 보안팀이 할까?

즉 Provider–Customer 경계가 명확해져도 Customer 내부의 책임경계는 자동으로 정리되지 않는다.

이 글의 중심 질문
Shared Responsibility를 Cloud Provider와 Customer의 기술경계에서 끝내지 않고, 기업 내부의 역할·권한·증적·Risk Ownership까지 확장하려면 어떤 구조가 필요한가?

1. IaaS·PaaS·SaaS마다 책임의 위치가 이동한다

IaaS에서는 고객이 OS, Middleware, Network Policy, IAM을 더 많이 관리하고 SaaS에서는 애플리케이션 자체의 운영은 Provider가 맡는다. 그러나 SaaS에서도 사용자 계정, Data Classification, Sharing Policy, Retention, Access Review는 고객책임으로 남는 경우가 많다.

따라서 ‘Cloud이기 때문에 Provider가 알아서 한다’는 기대는 위험하다. 서비스모델이 바뀌면 사라지는 책임과 이동하는 책임을 구분해야 한다.

특히 Managed Service가 늘어날수록 기술운영은 줄어들지만 Governance와 Configuration 책임은 더 중요해질 수 있다.

2. ‘Private Network’만으로 접근통제가 완성되지 않는다

VPN, Private Link, Internal Network를 통해 Cloud Console이나 서버에 접근하도록 제한하면 공격면을 줄일 수 있다. 그러나 이 통제는 접근경로를 제한하는 것이지 주체·권한·세션을 완전히 설명하지 않는다.

누가 접속했는지, 어떤 Role을 사용했는지, 특권권한이 상시인지, 세션이 기록되는지, 접근이 업무목적과 일치하는지까지 봐야 한다.

그래서 Cloud 관리자 접근통제는 Network Path + Identity + Privilege + Session + Audit의 결합으로 설계해야 한다.

통제층질문예시
Network Path어디에서 접속 가능한가VPN·ZTNA·Private Endpoint
Identity누가 접속하는가SSO·MFA·Federation
Privilege무엇을 할 수 있는가Role·JIT·Permission Boundary
Session실제 무엇을 했는가Session Recording·Command Log
Audit나중에 증명 가능한가CloudTrail·Access Review·Change History

3. 내부 R&R은 기술계층보다 Decision Type으로 나누는 편이 낫다

Cloud 환경에서는 Platform팀, 개발팀, 보안팀, Data Owner가 같은 자원을 서로 다른 관점으로 관리한다. 기술계층만으로 Owner를 지정하면 변경이 여러 팀에 걸쳐 있을 때 책임이 흐려질 수 있다.

예를 들어 Security Group의 표준정책은 Security가 정하지만 특정 Port를 열어야 하는 업무필요성은 Application Owner가 설명해야 하고 잔여위험은 Risk Owner가 수용해야 한다.

그래서 Build·Approve·Operate·Review처럼 Decision Type으로 R&R을 나누는 방법이 유용하다.

01

Standard Owner

Landing Zone·IAM·Logging의 기본 Guardrail

02

Change Owner

특정 Workload 변경의 기술책임

03

Risk Owner

예외·잔여위험을 수용하는 사업/서비스 책임

04

Evidence Owner

Audit·Access Review·Finding Closure 증적 관리

4. Shared Responsibility의 실효성은 Evidence에서 확인된다

책임표를 만들어도 실제 운영증적이 없으면 책임경계는 형식적일 수 있다. 누가 Firewall Rule을 승인했는지, IAM Role이 언제 바뀌었는지, GuardDuty Finding이 누가 조치했는지 기록이 남아야 한다.

Cloud는 API 기반이기 때문에 오히려 Evidence 자동화에 유리하다. Config Snapshot, Audit Log, IaC Change, Ticket ID를 연결하면 정책과 실제 상태의 차이를 지속적으로 확인할 수 있다.

이렇게 보면 Cloud Governance의 성숙도는 문서의 RACI보다 Control Evidence의 자동화 정도로 평가할 수 있다.

5. Cloud Security는 ‘책임 공유’보다 ‘책임 연결’의 문제다

Shared Responsibility라는 표현은 책임이 분산된 것처럼 들리지만 실제로는 한 서비스의 안전성을 위해 여러 책임이 연결되어 있다. 하나의 연결이 끊기면 통제공백이 생긴다.

Provider가 안전한 서비스를 제공해도 Customer가 Root MFA를 하지 않으면 위험하고, Security가 표준정책을 만들어도 개발팀이 예외를 장기간 방치하면 위험하다.

따라서 Cloud Security Governance는 책임을 나누는 것과 동시에 End-to-End로 연결하는 구조가 필요하다.

RESEARCHER'S NOTE

AWS 접근통제를 운영하면서 외부접속을 VPN 경로로 제한하고 로그를 검토하는 작업을 해보면 ‘Private하게 연결됐다’는 사실만으로 통제가 끝나지 않는다는 점이 명확했다. 결국 누가 어떤 권한으로 무엇을 했는지가 남아야 한다.

그래서 Shared Responsibility를 Provider의 문서 한 장으로 이해하기보다 조직 내부의 Decision Right와 Evidence Architecture로 확장해서 보는 것이 실무적으로 중요하다고 생각한다.

LIMITATION

Cloud 서비스별 책임경계와 Provider 기능은 계속 변한다. 특정 서비스의 세부 통제는 공식 Provider 문서와 계약조건을 확인해야 하며, 이 글은 기업 내부 Governance 구조에 초점을 둔다.
