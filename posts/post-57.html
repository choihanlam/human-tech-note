AI 에이전트 시대의 접근통제

사람의 권한을 그대로 복사하지 않고 Agent Identity·Delegated Token·Approval Gate를 설계하기

Research Archive · 2026년 7월 12일 약 14분#57 / 75

post-06에서는 Agent의 권한을 Identity와 Delegation, Accountability의 문제로 보았다. 이번 글에서는 한 단계 더 내려가 실제 시스템에서 무엇을 배치해야 하는지를 본다.

가장 위험한 구조는 사용자의 장기 Credential을 Agent가 그대로 들고 모든 Tool에 접근하는 방식이다. 구현은 쉽지만 Actor와 Principal이 섞이고, Scope와 만료를 줄이기 어렵다.

Agent Access Architecture의 최소 구성

Principal업무를 요청한 사람 또는 서비스
Agent Identity사람과 구분되는 고유 실행주체
Delegated TokenResource·Scope·TTL이 제한된 업무별 권한
Policy Engine목적·민감도·위험수준에 따라 Allow/Step-up/Deny
Tool Gateway직접 Credential 노출 없이 실제 API 호출 집행
Audit Chain요청자→Agent→정책→Tool→결과를 하나의 Trace로 연결

사람의 권한을 복사하지 않고 ‘업무 권한’을 발급한다

Approval Gate는 Tool 앞에 둔다

Action기본 처리추가 통제
내부 검색·요약자동 허용Data Classification 필터
읽기 API정책 기반 자동Resource/Rate 제한
외부 메일·전송조건부수신자·민감정보·Human Approval
권한 변경사람 승인Step-up MFA·이중승인
Production 변경사람 승인 + CanaryRollback·Change Window

Agent의 ‘직접 Tool 접근’을 최소화한다

Agent가 각 시스템 Credential을 직접 보유하면 Secret Rotation과 권한회수가 복잡해진다. Tool Gateway나 Broker가 Agent의 요청을 검증하고 실제 Credential을 대신 사용하면 Credential 노출과 Scope 확장을 줄일 수 있다.

Agent가 Tool 호출 요청
Mandate·Scope·Resource 일치 → Risk 평가
불일치 → Deny + Audit
낮은 위험 → 실행
높은 위험 → Human Approval / Step-up
