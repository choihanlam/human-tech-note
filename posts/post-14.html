AI Agent 생태계는 새로운 공급망 위험을 만드는가

Model·MCP·Tool·Plugin·API가 연결될수록 넓어지는 Trust Boundary와 ‘권한 공급망’

소프트웨어 공급망 보안은 오랫동안 Library, Package, Build Pipeline, Artifact의 신뢰성을 다뤄왔다. Agentic AI는 여기에 새로운 구성요소를 추가한다. Foundation Model, System Prompt, RAG Source, MCP Server, Plugin, Tool, 외부 API, Credential과 다른 Agent가 하나의 실행흐름으로 연결된다.

중요한 차이는 이 구성요소들이 코드만 전달하는 것이 아니라 행동할 권한까지 연결한다는 점이다. 취약한 Package는 코드를 오염시킬 수 있고, 악성 Tool이나 조작된 MCP Server는 Agent가 실제 외부행동을 하도록 유도할 수 있다.

그래서 Agent 시대의 공급망을 SBOM만으로 설명하기 어렵다. 무엇이 설치되어 있는지와 함께 ‘어떤 구성요소가 어떤 권한으로 무엇을 할 수 있는지’를 봐야 한다.

이 글의 중심 질문
AI Agent의 공급망 위험을 소프트웨어 구성요소의 무결성뿐 아니라 Model·Data·Tool·Credential·Delegation이 연결되는 ‘권한 공급망’으로 확장해 관리해야 하는가?

1. NIST와 OWASP가 Agent 보안에서 Tool Use를 강조하는 이유

NIST는 2025년부터 Agent Tool Use에 대한 Taxonomy와 보안연구를 진행했고, 2026년 Agent Security RFI에서도 Tool 접근과 외부시스템 상호작용을 핵심 위험으로 다뤘다. OWASP GenAI Security에서도 Excessive Agency, Supply Chain, Sensitive Information Disclosure 같은 위험이 반복적으로 강조된다.

Agent는 모델 출력만 생성하는 것이 아니라 Tool을 통해 파일을 쓰고 메일을 보내고 API를 호출한다. 따라서 Tool의 설명, 입력값, 반환결과가 모두 Agent의 다음 의사결정에 영향을 줄 수 있다.

기존 Software Dependency가 ‘무엇을 실행하는가’의 문제였다면 Agent Dependency는 ‘무엇을 실행할 권한이 생기는가’까지 포함한다.

2026

2026

Supply Chain·Excessive Agency·Prompt Injection을 주요 위험으로 제시

2. SBOM에서 ‘Agent BOM’으로 확장해야 한다

SBOM은 Software Component의 출처와 버전을 가시화한다. Agent 환경에서도 이 원칙은 중요하지만 목록이 더 넓어져야 한다. 어떤 Model을 어떤 Version으로 쓰는지, 어떤 RAG Source를 참고하는지, 어떤 MCP Server와 Tool을 연결하는지, 어떤 Credential Scope를 갖는지를 함께 알아야 한다.

특히 SaaS형 Agent Platform은 Runtime에 Tool이 추가되거나 사용자가 Plugin을 연결할 수 있다. 정적 배포목록만으로 실제 실행경로를 알기 어렵다.

그래서 Agent Inventory는 Software BOM + Model/Data/Tool Inventory + Authority Graph의 결합으로 생각할 수 있다.

3. Trust Boundary는 연결마다 새로 생긴다

Agent가 내부 RAG를 읽고 외부 MCP Server를 거쳐 SaaS API를 호출한다면 데이터는 여러 신뢰영역을 통과한다. 각 경계마다 Authentication, Authorization, Data Minimization, Output Validation이 달라진다.

이때 Vendor Security Review를 한 번 수행했다고 전체 경로가 안전해지는 것은 아니다. Model Provider는 안전해도 연결된 Tool이 과도한 권한을 가질 수 있고, Tool은 안전해도 Agent가 민감정보를 잘못 전달할 수 있다.

Architecture Diagram에서 Data Flow와 Authority Flow를 동시에 그려야 하는 이유다.

4. C-SCRM의 기본원칙은 Agent 환경에서도 그대로 살아 있다

NIST CSF 2.0의 C-SCRM 가이드는 공급업체 요구사항, Due Diligence, 공급망 Visibility, 지속적 모니터링을 강조한다. Agent 환경에서도 공급자 평가, Provenance, 변경관리, Incident Notification은 여전히 중요하다.

다만 Agent는 Runtime 연결이 동적으로 바뀔 수 있으므로 조달 시점 검토만으로 충분하지 않다. 어떤 Tool이 새로 연결됐는지, Permission이 바뀌었는지, Model Version이 업데이트됐는지 운영 중 지속적으로 추적해야 한다.

이는 Software Supply Chain과 SaaS Governance가 결합되는 지점이다.

01

Due Diligence

Model·Tool Provider의 보안·운영·데이터정책 평가

02

Runtime Visibility

실제 연결된 Tool·Endpoint·Credential 변화 추적

03

Change Control

Model·Plugin·MCP 업데이트의 영향 검증

04

Exit & Containment

Provider 문제 시 차단·대체·Credential 회수 경로 준비

5. ‘권한 공급망’이라는 관점이 필요한 이유

Agent가 다른 Agent에게 작업을 넘기거나 Tool이 또 다른 API를 호출하면 Authority가 여러 단계를 거친다. 원래 사용자가 허용한 목적이 하위 Tool까지 일관되게 전달되지 않으면 중간구성요소가 필요 이상의 권한을 사용할 수 있다.

따라서 공급망 보안에는 Provenance뿐 아니라 Delegation Provenance가 필요하다. 어떤 권한이 어느 Principal에서 출발했고 어떤 변환을 거쳤는지 추적해야 한다.

이 구조가 만들어지면 특정 Tool이나 Vendor가 취약해졌을 때 어떤 Agent와 업무가 영향을 받는지 빠르게 역추적할 수 있다.

RESEARCHER'S NOTE

내가 Agent Supply Chain에서 특히 주목하는 것은 ‘새로운 Vendor가 많아진다’는 사실보다 권한의 경로가 길어진다는 점이다. 기존 SaaS도 복잡했지만 Agent는 여러 SaaS와 API를 한 번의 의도로 연결해 행동할 수 있다. 작은 설정 하나가 더 넓은 Blast Radius를 만들 수 있다.

그래서 Agent 보안자산을 모델·Token·Tool·Workflow까지 확장해서 봐야 한다. 자산관리와 권한관리를 따로 보던 방식이 Agent 환경에서는 하나의 그래프로 합쳐질 가능성이 높다.

LIMITATION

MCP와 Agent Protocol 생태계는 빠르게 변화하고 있으며 표준과 보안 Best Practice도 아직 형성 중이다. 특정 Tool Protocol의 현재 취약점을 전체 Agent Architecture의 일반적 특성으로 과도하게 일반화하지 않아야 한다.
