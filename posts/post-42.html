KPI·Compliance·Risk를 요구사항으로 바꾸는 법

기능이 ‘동작한다’에서 끝나지 않고 운영·감사·복구까지 완료조건에 넣기

Research Archive · 2026년 7월 21일 약 12분#42 / 75

요구사항 문서는 기능을 잘 설명한다. 로그인, 조회, 등록, 승인 같은 기능은 화면과 API로 확인하기 쉽다. 그러나 서비스가 실제 운영에 들어가면 기능만큼 중요한 것이 있다. 얼마나 빨라야 하는가, 누가 접근할 수 있는가, 로그는 남는가, 장애 시 어떻게 복구하는가 같은 조건이다.

이 조건이 문서에서 빠지면 프로젝트 막판에 보안팀·운영팀·감사 요구가 갑자기 추가된 것처럼 보인다. 사실은 처음부터 서비스의 일부였어야 한다.

‘정책’이라는 문장을 시스템이 검증할 수 있는 조건으로 바꾼다

추상적 요구검증 가능한 요구로 변환검증 방법
접근통제를 강화한다관리자 기능은 MFA+지정 Role만 허용미인가 계정 403 / 권한변경 Log 확인
개인정보를 안전하게 처리한다Export는 승인된 Role·건수 제한·감사로그대량 Export Negative Test
가용성을 확보한다핵심 API p95·오류율·RTO 기준 설정부하·장애전환·복구시험
법규를 준수한다보존·삭제·접근증적을 시스템 기능에 반영Retention Job·Audit Evidence

Acceptance Criteria는 ‘개발 완료’의 정의를 바꾼다

기능 요청: “신규 API로 잔고를 조회한다.”
정상 경로
유효한 서비스가 기대한 데이터를 반환하는가?
미인가 경로
권한 없는 서비스가 403으로 차단되는가?
운영
p95·오류율이 기준을 충족하는가?
증적
어떤 정책·버전·요청이 처리됐는지 남는가?

이렇게 요구사항을 쓰면 보안은 ‘사후 검토’가 아니라 완료조건의 일부가 된다.

KPI와 Risk를 같은 문서에 놓는 이유

PM에게 요구사항은 통제의 언어이기도 하다

PROJECT NOTE

보안과 운영 경험을 거친 뒤 요구사항을 볼 때 가장 달라진 점은 “무엇을 만들 것인가”와 함께 “어떤 조건을 만족해야 안전하게 바꿀 수 있는가”를 보게 된 것이다. KPI와 Risk를 Acceptance Criteria에 넣으면 부서 간 책임도 선명해진다.
