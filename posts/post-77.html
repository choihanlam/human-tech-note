정상적인 API 요청은 왜 보안 위협이 되는가

AI 에이전트 시대, WAF·IPS 이후의 접근통제와 행위 기반 보안

Research Archive · 2026년 11월 6일 약 12분#77

01 · 공격이 정상 요청처럼 보이는 이유

WAF에서 허용된 요청이 곧 안전한 요청일까? 실제 보안 운영에서 이 둘은 서로 다른 판단이다. WAF는 주로 HTTP 요청의 패턴과 정책을 검사하지만, 특정 사용자가 특정 주문·정산·개인정보 객체를 열람할 권한까지 항상 알 수 있는 것은 아니다.

공격자가 취약한 API를 악용하는 데 반드시 비정상적인 문자열이 필요한 것은 아니다. 정상적인 로그인 이후 서버가 객체 소유권을 확인하지 않는다면 요청 형식은 유효해도 결과는 부당할 수 있다. 다만 '정상 요청이므로 탐지 불가능하다'는 결론도 틀리다. 권한 실패, 객체 접근 분포, 세션의 행위 흐름이 관측된다면 탐지 단서가 남는다.

요청의 문법적 유효성, 사용자의 인증 상태, 데이터 접근의 정당성은 서로 다른 검증 단계다.

02 · SPA·MPA와 API 공격표면: 화면 밖에서 무엇이 보이는가

SPA(Single Page Application)는 초기 HTML을 받은 뒤 JavaScript가 화면 상태를 갱신하며 API를 호출하는 형태가 일반적이다. MPA(Multi Page Application)는 페이지 이동마다 서버가 새 문서를 반환하는 형태가 일반적이다. 그러나 이 구분만으로 보안 수준을 판단할 수는 없다. 두 방식 모두 브라우저와 서버 사이의 API 또는 HTTP 엔드포인트를 가진다.

브라우저 개발자도구의 Network 패널에는 실제 호출된 URL, 메서드, 응답 상태, 일부 요청·응답 구조가 보일 수 있다. JavaScript 번들에는 경로 문자열이 포함될 수 있지만, 발견된 경로가 실제 활성 API인지, 접근 가능한지, 취약한지는 별도로 검증해야 한다. 클라이언트에 보이는 메뉴나 버튼을 숨기는 것은 서버 측 인가의 대체재가 아니다.

관찰 대상알 수 있는 것그 자체로 알 수 없는 것
브라우저 화면사용자에게 노출된 기능·동선서버의 전체 권한 정책
Network 요청호출 경로·메서드·상태코드타인 객체 접근 허용 여부
JavaScript 번들클라이언트 코드에 포함된 경로 후보실제 서버의 활성화·인가 상태
서버 감사로그구현 수준에 따라 주체·객체·결과로그에 기록하지 않은 업무 의도

따라서 공격표면 관리의 출발점은 공개 화면의 경로를 세는 일이 아니라, 운영 중인 API·데이터 객체·인증 방식·권한 모델을 자산으로 연결하는 것이다.

03 · Firewall, IPS, WAF, API Gateway는 각각 무엇을 검증하는가

네트워크 방화벽은 주로 통신 경로와 주소·포트 기반 정책을 적용한다. IPS는 알려진 침입 징후와 탐지 규칙을 활용하며, WAF는 HTTP 계층의 악성 패턴과 정책 위반을 검사한다. API Gateway는 라우팅, 인증 연계, 요청 제한, 로깅 등을 제공할 수 있지만 실제 제공 기능은 제품과 설정에 따라 달라진다.

WAF를 통과했다고 서버가 신뢰해도 된다는 뜻은 아니다. 반대로 WAF가 아무 역할도 못 한다는 뜻도 아니다. 악성 페이로드 차단, 속도 제한, 이상 트래픽 탐지 등은 여전히 유효하다. 서로 다른 통제의 책임을 혼동하지 않는 것이 중요하다.

04 · BOLA, BFLA, BOPLA와 비즈니스 로직 악용의 차이

OWASP API Security Top 10(2023)은 API 위험을 여러 범주로 나눈다. 이 구분을 정확히 이해해야 취약점 점검 범위와 담당 조직을 정할 수 있다.

유형핵심 결함방어 검증 질문
API1 · BOLA객체별 소유권·접근권한 미검증이 사용자가 이 주문·문서를 조회할 수 있는가?
API3 · BOPLA객체 속성 수준의 노출·수정 통제 부족허용되지 않은 필드가 반환·수정되는가?
API5 · BFLA기능 수준 권한 검증 부족일반 사용자가 관리자 기능을 실행할 수 있는가?
API6 · Sensitive Business Flows민감한 업무 흐름에 대한 무제한 접근자동화된 반복 행위가 업무·서비스에 피해를 주는가?

예컨대 고객이 자기 주문을 조회하는 것은 정상이다. 다른 고객의 주문을 조회할 수 있다면 객체 수준 인가를 의심해야 한다. 반면 주문 조회 응답에 내부 정산용 필드가 불필요하게 포함되면 속성 수준 노출 문제를 검토해야 한다. 고객이 관리자 전용 환불 승인 기능을 호출할 수 있다면 기능 수준 인가 문제다.

이 사례들은 설명을 위한 가상 상황이다. 실제 취약 여부는 서버 구현과 권한 정책을 확인해야 판단할 수 있다.

05 · AI 에이전트의 자동화가 위협 모델에 추가하는 것

브라우저 자동화, API 경로 분석, 반복적인 탐색은 AI 이전에도 존재했다. AI 에이전트는 여러 관찰 결과를 요약하고 다음 분석 단계를 선택하는 데 도움을 줄 수 있다. 하지만 특정 도구를 사용했다는 사실만으로 공격 성공률이 높거나 탐지 회피가 보장된다고 주장할 수는 없다.

공유된 사례에서 소개된 API 정찰, 브라우저 자동화, 발견 결과 저장은 각각 공격표면 파악·사용자 동작 재현·조사 결과 관리에 해당한다. 이러한 기능은 허가된 보안점검에도 쓰인다. 실제 위험은 도구 자체보다 사용 권한, 점검 범위, 대상 시스템의 인가 결함에 달려 있다.

특히 '무차별 요청과 로그인 실패를 하지 않으면 탐지되지 않는다'는 해석은 과도하다. 성공한 조회라도 비정상적인 객체 다양성, 접근 시간, 업무 맥락, 호출 순서가 탐지 단서가 될 수 있다. 물론 로그가 충분하지 않으면 이를 재구성하기 어렵다.

06 · 탐지는 HTTP 한 줄이 아니라 세션·객체의 관계를 읽는 일

가상의 개인정보 조회 서비스를 생각해 보자. 동일한 계정이 정상 로그인한 뒤 여러 고객 객체를 연속 조회한다. 단일 요청은 모두 200 OK일 수 있다. 그러나 해당 계정의 역할과 조회 대상 사이에 일관성이 없다면 조사가 필요하다.

분석 시에는 ① 요청 주체가 누구인지 ② 어떤 권한으로 접근했는지 ③ 어떤 데이터 객체를 요청했는지 ④ 허용·거부 결과가 무엇인지 ⑤ 같은 세션에서 이전·이후에 어떤 행위가 있었는지 확인한다.

대량 조회만으로 공격을 단정해서는 안 된다. 고객지원 담당자의 정상 업무, 배치 처리, 권한 변경 직후의 행위가 오탐 원인이 될 수 있다. 탐지 규칙에는 예외 승인과 사후 검토 절차가 함께 필요하다.

07 · 개발·배포 단계에서 검증해야 할 통제

취약점 진단은 알려진 공격 문자열을 찾아내는 일로 끝나지 않는다. API별 역할과 객체 권한을 정의하고, 허가된 테스트 계정과 가상 데이터로 권한 경계를 확인해야 한다. 정상 사용자 A의 객체를 사용자 B가 조회할 수 없는지, 일반 역할이 관리자 기능을 실행할 수 없는지, 불필요한 응답 속성이 노출되지 않는지를 검증하는 방식이다.

단계확인 항목남겨야 할 증적
설계API 자산·데이터 등급·역할 정의API 명세·권한 매트릭스
개발서버 측 인가·최소권한 구현코드 리뷰·단위 테스트
배포 전역할·객체별 부정 테스트테스트 결과·결함 조치
운영권한 실패·이상행위·로그 연계탐지 이력·조사·재발방지

이때 보안팀만으로 업무 권한을 설계하기 어렵다. 서비스 오너는 어떤 데이터 접근이 정당한지 정의하고, 개발팀은 서버 검증을 구현하며, 인프라·보안 운영은 로그와 통제의 동작을 확인해야 한다.

08 · ISMS-P와 보안투자 관점에서의 운영 모델

API 권한 검증은 접근통제와 개발보안, 로그 관리, 사고 대응의 교차점에 있다. ISMS-P 운영에서도 개별 솔루션의 설치 여부보다 정책이 시스템에서 실제로 집행되는지, 그 결과를 어떤 증적으로 확인할 수 있는지가 중요하다. 특정 인증 항목과의 공식 대응 관계는 최신 인증기준 원문으로 별도 확인해야 한다.

예산이 한정돼 있다면 WAF 추가 구매 이전에 API 인벤토리의 정확성, 객체별 인가 테스트 커버리지, 중요 로그의 상관분석 가능성, 개선조치 완료율을 확인할 필요가 있다. 통제의 우선순위는 개인정보 영향도, 노출 가능성, 악용 시 피해, 개선 비용을 함께 평가해 정한다.

보안 운영의 성과는 장비의 개수만으로 설명되지 않는다. 누락된 권한 검증을 얼마나 발견했는지, 사고 의심 세션을 얼마나 빨리 재구성할 수 있는지, 재발 방지 조치가 개발·배포 프로세스에 반영됐는지로 평가할 수 있다.

마치며 · 정상처럼 보이는 행위의 정당성을 묻다

AI 에이전트가 새로운 종류의 권한 취약점을 만들어낸 것은 아니다. 다만 웹 화면과 API를 분석하고 반복적인 작업을 자동화하는 비용을 낮출 수 있다. 따라서 방어자는 단일 페이로드 탐지에 머무르지 않고 API 인가, 업무 흐름, 세션 로그, 개발·운영 책임을 연결해야 한다.

보안의 질문은 '공격처럼 보이는가?'에서 '이 사용자에게 이 행위가 정당한가?'까지 확장되어야 한다.
