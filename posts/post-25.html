Kubernetes 보안은 왜 NetworkPolicy만으로 끝나지 않는가

Workload Identity·Admission·Secret·Runtime·Supply Chain을 배포 생명주기 전체에서 연결하기

Research Archive · 2026년 10월 12일 약 14분#25 / 75

Kubernetes 보안을 처음 공부하면 NetworkPolicy가 눈에 잘 들어온다. Pod 간 통신을 제한하고 Namespace 경계를 세우는 것은 중요하다. 하지만 위험한 Container가 배포되거나 ServiceAccount가 Cluster-wide 권한을 가지고 있거나 Secret이 노출되어 있다면 NetworkPolicy만으로 충분하지 않다.

Kubernetes의 특징은 배포·권한·네트워크·Runtime이 빠르게 변한다는 점이다. 사람이 Console에서 하나씩 설정하는 방식보다 Manifest, Helm, GitOps, Admission Policy가 실제 운영상태를 결정한다.

그래서 Kubernetes 보안은 ‘어떤 솔루션을 설치했는가’보다 Build부터 Runtime까지 어떤 Guardrail이 자동으로 집행되는가를 보는 편이 정확하다.

이 글의 중심 질문
Kubernetes의 보안통제를 Network Segmentation이 아니라 Workload Lifecycle 전체의 Policy-as-Code와 검증 가능한 Guardrail로 설계하면 무엇이 달라지는가?

1. Workload Identity가 네트워크보다 먼저다

Pod는 ServiceAccount를 통해 Kubernetes API 또는 외부서비스에 접근할 수 있다. 기본 ServiceAccount를 광범위하게 사용하거나 ClusterRoleBinding이 과도하면 하나의 Workload 침해가 더 넓은 권한으로 이어질 수 있다.

NIST SP 800-207A도 Cloud-native Zero Trust에서 IP나 네트워크위치보다 Application·Service Identity를 중심으로 접근통제를 설계하는 방향을 강조한다.

따라서 Pod가 어디에 있는지보다 어떤 Service Identity를 가지고 어떤 Resource에 접근하는지를 먼저 확인해야 한다.

2. Admission Control은 Production에 들어가기 전 마지막 정책집행 지점이다

Runtime에서 위험한 행동을 탐지하는 것도 중요하지만 Privileged Container, HostPath, HostNetwork, Root User 같은 설정을 배포 전에 막는 편이 비용이 낮다.

Pod Security Admission이나 Policy Engine을 통해 조직의 최소기준을 코드로 집행하면 개발팀마다 해석이 달라지는 문제를 줄일 수 있다.

Policy-as-Code의 장점은 ‘문서에 있는 보안기준’과 ‘실제 Cluster가 허용하는 설정’ 사이의 거리를 줄인다는 점이다.

3. Secret 관리와 Supply Chain은 분리해서 볼 수 없다

Kubernetes Secret은 기본적으로 민감정보 저장소의 모든 요구를 해결하는 기능이 아니다. Manifest, Git, CI/CD, Environment Variable에 Secret이 노출되는 경로를 함께 봐야 한다.

외부 Secret Manager와 KMS를 사용하고 Rotation과 Access Audit를 연결하면 Secret Lifecycle을 더 일관되게 관리할 수 있다.

동시에 Container Image와 Dependency의 Provenance도 중요하다. 신뢰된 Build Pipeline과 Registry, Image Signature, SBOM이 연결되어야 배포하는 Artifact의 출처를 설명할 수 있다.

4. 핵심통제는 ‘설정했는가’보다 ‘실제로 막히는가’를 시험해야 한다

NetworkPolicy 파일이 존재한다고 Direct Access가 반드시 차단되는 것은 아니다. CNI 구현과 Namespace Label, Default Deny 여부에 따라 실제 결과가 다를 수 있다.

RBAC도 Role YAML만 봐서는 실제 Effective Permission을 놓칠 수 있다. 그래서 미인가 ServiceAccount로 API를 호출하거나 Backend Direct Access를 시도하는 Negative Test가 중요하다.

변경 전·후에 ‘정상 호출은 성공하고 미인가 호출은 실패하는가’를 자동시험하면 Security Control을 배포품질의 일부로 만들 수 있다.

5. Kubernetes 보안은 Platform Engineering과 만난다

개별 개발팀이 모든 Security Policy를 직접 설계하도록 하면 속도도 느리고 일관성도 낮아진다. Platform팀이 Secure Default, Namespace Template, Approved Base Image, Standard Logging을 제공하면 개발자는 Guardrail 안에서 빠르게 배포할 수 있다.

이 구조는 중앙보안팀이 모든 Manifest를 승인하는 방식보다 확장성이 높다. 보안정책을 Platform Capability로 제품화하는 셈이다.

결국 Kubernetes Security는 개발과 보안의 충돌보다 공통 Platform을 얼마나 잘 설계하는지에 달려 있다.

RESEARCHER'S NOTE

Kubernetes를 직접 운영한 전문경험을 과장해서 말할 필요는 없다. 다만 MSA·Cloud 보안과 접근통제를 검토하면서 반복해서 마주친 원칙은 ‘정책과 실제 집행이 일치하는지 확인해야 한다’는 것이었다. Kubernetes는 이 원칙이 가장 선명하게 드러나는 환경 중 하나다.

특히 보안정책을 YAML로 작성했다는 사실보다 정상·미인가 요청을 통해 결과를 검증하고 그 Evidence를 변경완료 조건에 넣는 방식에 관심이 있다.
